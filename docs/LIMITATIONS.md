# 已知限制

本工具是什么、以及**明确不是什么**。这份文档的用途是让你在提交到一篇论文之前
先读完，避免"能量是负的所以结果是对的"这类误判。

相关：[`VERIFICATION.md`](VERIFICATION.md)（实际跑了什么）、
[`SCORING.md`](SCORING.md)（算法细节与偏离）。

---

## 1. 最要紧的一条

**本工具目前不是一个被验证过能正确预测结合姿势的工具。**

它是一个结构完整、单元测试覆盖到数值正确性、GPU 与 CPU 数值一致、
但**尚未与 AutoDock Vina 做交叉数值比对**的引擎。

具体来说，以下问题还没有证据：

- 预测能量与 Vina 差多少（**没有交叉数值比对**，见 §3.1）；
- RMSD 聚类阈值在实际数据上是否合适；
- **盲视对接**能不能自己找对口袋（回对接用的是已知位点盒，见 §2.1）。

「pose 落在正确口袋」这一条**部分**有了证据（回对接基准），不再是完全空白。

**本轮测出并已修复一条曾经最要紧的缺陷**（见 §3.2，保留为记录）：
**分子间能量里的氢键项曾经只对同元素供受体成立，跨元素氢键贡献精确 0.000000，
且受体里缺席的元素会让配体里对应的原子连排斥都不参与。** 网格的元素维度现在是
**探针类型**而不是对受体的过滤，跨元素对实测给出非零值。§3.2 里那套数字是
**修复前**的，不要当成现在的行为。

如果你的用途是**筛选**（这个配体值不值得进一步研究），风险可控。
如果用途是**结构假设**（这个配体是怎么结合的），请先用 Vina 跑一遍做交叉验证——
而且要知道本工具的氢键项与 Vina 的**不是同一套定义**（§3.1、§4），所以那次对照
不只是在比常数。

## 2. 验证覆盖的边界

| 维度 | 状态 |
|---|---|
| 平台 | 只在 Windows 11 x86_64 验证。macOS (Metal) / Linux (Vulkan) **未测** |
| GPU | 只在 NVIDIA RTX 3050 Laptop 验证。AMD 独显 / Intel 核显 / Apple Silicon **未测** |
| 受体 | 真实蛋白测过 **crambin (1CRN, 46 残基)**，以及回对接基准里的 8 个结构（1HVR、3PTB 等，见 `VERIFICATION.md` §3.7）。**盲视对接没有验证** |
| 配体 | 小分子（苯、甲苯、苯酚、布洛芬、生物素、沙丁胺醇），**没有肽段、核酸、金属配合物** |
| 对接 | 回对接跑的是 39 × 26 × 41 Å 级的口袋盒与 `exhaustiveness` 8–128。**没有系统的大盒子 / 高 throughput 数据** |
| GUI | 渲染层与交互控件用真实 Qt 事件验证，脚本是 `workbench_interaction_check.py`。**上一版写的"44 项"已过期**：该文件现有 193 个 `check(` 调用点、21 个 `section(`。**本轮未能取得实际执行条数**——这台机器没有 OpenGL 上下文（`workbench_smoke` 以 `no Qt GL context` 结束），所以这里给出的是静态计数，不是跑出来的数字。**未测**：多显示器 / 混合 DPI 缩放、触屏与三键鼠标以外的输入设备、窗口在后台时长时间运行的稳定性 |

### 2.1 回对接：跑过了，但**本文件上一版说它没跑过，那是错的**

上一版这里写「**本工具从未被验证过能把一个已知结合的配体放回它的口袋**」。
这句话现在是**假的**，而且属于最坏的一种错：一个已经不再成立的限制会让读者
主动放弃一个本来能用的工具，所以它比漏写限制更糟。

实际情况：

* `scripts/redock_benchmark.py` 就是这个验证，结果记在
  [`VERIFICATION.md`](VERIFICATION.md) §3.7 与其中的基准表里。
  `opendocking.core.exhaustiveness_for_box` 的 docstring 里那句
  「3PTB 位点盒 39 × 26 × 41 Å，exhaustiveness 16 → 12.88 Å RMSD，
  64 → 1.26 Å」就是从这里来的。
* 它**不是 CI 门禁**，因为它要联网取结构、每个案例都跑一次真实搜索。
  本轮**无法离线复现**：需要从 RCSB 下载，本机出网被拦。所以下面这些数字
  我只能转述，不能核对。

**仍然成立、且不要因为上面那句被撤销而忽略的：**

* **"能量函数是合理的"仍然只是间接证据。** 回对接测的是「搜索能不能找回一个
  已知构象」，它同时经过打分函数和搜索两层，任何一层坏掉都可能互相掩盖。
* **输入本身有已知缺陷，所以那些数字是下限而不是测量值。**
  `redock_benchmark.py` 自己的 docstring 写明：晶体结构里的配体不带键，
  脚本按原子间距推断连接性，这会**把芳香性和形式电荷弄错**，从而同时改变
  可旋转键集合和部分电荷。
* **绝对 kcal/mol 仍然不能和 Vina 或文献比较**（见 §3.1），这条没有因为
  回对接跑过而放松半分。
* **多构象盲视（blind docking）没有验证。** 回对接用的是已知的结合位点盒，
  「不知道位点在哪」这个更难的问题依然没有证据。

## 3. 经验打分函数本身的限制

这不是本工具独有的问题，但使用者必须知道。

- **经验打分函数的姿势预测能力有限**。Vina 打分函数在它自己论文的基准集上，
  正确姿势的判别成功率明显低于 100%（原文报告的数量级在 60% 附近，
  以 ROCS 指标衡量）。
  **注意：这个数字本仓库没有重新核实过**，写在这里只是提醒量级，
  不是引用来论证。本工具复现的是 Vina 的**势函数**，不是它的预测能力。
  它是筛选工具，不是判决工具。
- **只有短程项，没有显式静电项**。带电配体、带电口袋（Asp/Glu/Lys/Arg）体系的
  打分误差会明显变大。Vina 1.2 也有同样的问题。
- **没有溶剂化项**。埋藏与暴露的区分是间接的、粗糙的。
- **没有扭转熵项**。柔性配体的打分会偏好展开构象。
- **Vinardo 的重参数化是否复现正确，未经验证**（见 §1）。

### 3.1 相互作用半径没有与 Vina 交叉验证

本轮修掉了一个真实缺陷：所有重原子的相互作用半径曾经统一取 0.4 Å，
导致氢键项在任何真实氢键距离上恒为零、全部吸引项落进碰撞区
（细节见 [`SCORING.md` §1.1](SCORING.md)）。修法是改用每元素的 XS 半径。

**但这些常数是按参考非键接触距离取的，没有与 AutoDock Vina 的二进制比对过。**
因此：

* 本工具输出的**绝对 kcal/mol 数字不应**与 Vina 输出或文献值直接比较；
* 相对排序、pose 质量、几何合理性都可以用，绝对亲和力不可以。

`docs/VERIFICATION.md` §1 记录了这个阻塞项的具体原因（出网被拦，装不了 `vina` 包）。

### 3.2 跨元素氢键曾经恒为精确零（**已修复**，本节保留为记录）

> **状态：已修复。** 下面记的是**修复前**的实测，不是现在的行为。现在跨元素对
> **给出非零值**，实测见本节末尾的表。保留这一节是因为它记录了引擎一次真实的
> 分块缺陷，以及它是怎么被测出来的。

**这一条曾经比 §3.1 更要紧，因为它改变的是「能量里还剩下什么」，而不是常数准不准。**

分子间能量走受体网格。**修复前**，每个受体原子只往自己元素的那一块里写
（当时记作 `grid.rs:418`），每个配体原子只读自己元素的那一块。两者只有在元素类相同
（`C/N/O/P/S/F/Cl/Br/I/Met`，`types.rs:773`）时才可能互相看到，表面的表面距离还按
`r − 2·R_self` 计算，即假定探针元素与受体原子相同。后果有两条，都是**精确的
0.000000**，不是「很小」：

1. **跨元素氢键一项都不给。** 最常见的 N–H···O = C 氢键贡献正好是 0。
   `VERIFICATION.md` 第 173 条记的「2.8 Å 处引擎给 0.000000，规范给 −0.335」——
   `−0.335` 复算确认（`N···O`，`d = 2.8 − 3.35 = −0.55`，公式给 `−0.335234`）。
   只有同元素的供受体（O···O、N···N、S···S）才拿得到氢键。
2. **受体里缺席的元素会让配体里对应的原子整个消失。** 形状项与排斥项和氢键项
   在同一块里，所以一个元素在受体里不存在，配体里所有该元素的原子对总能量的
   贡献就是精确 0——**连碰撞都不参与**。这不是边角情形：本仓库自己的受体夹具
   `examples/rec_prep.pdbqt` 是 `OA`×12 + `C`×12 + `HD`×6，**没有 N、没有 S**。

**修复。** 网格的**元素维度是探针类型，不是对受体的过滤**：每个受体原子现在写进
**每一个**探针元素的那一块，表面的表面距离改用探针自己的半径而不是
`r − 2·R_self`。`dock-core` 的 `grid.rs` 里有一条单测把这条语义钉住
（`a_receptor_atom_reaches_every_probe_type`，其注释直接记述了上面这个旧缺陷）。

**修复后的实测**（单原子受体 + 单原子配体，`spacing` 0.375，`score_conformation`；
与下表同口径）：

| 受体 \ 配体 | `C` | `N` | `O` | `S` |
|---|---|---|---|---|
| `C` | `−0.064285` | `−0.035675` | `−0.037476` | — |
| `N` | `−0.035675` | `−0.037476` | `−0.033468` | — |
| `O` | `−0.037476` | `−0.033468` | `−0.025221` | `−0.036903` |
| `S` | — | — | `−0.036903` | — |

（数值是 `r = 2.0 Å` 处的总能量。**异元素格全部非零**，这正是修复前后唯一需要
对照的差别；`r = 3.0 Å` 处这十对现在都是 `0.000000`，因为该距离上四项都不贡献，
与元素无关。）

**分子内项不走这条路**：它直接调 `pair_energy(a, b, d)`，按 `kind` 的
`can_donate`/`can_accept` 判断。修复前这造成了总能量两半对同一个概念用了两套定义；
网格侧已修，**两侧定义现已一致**。

**仍然成立的结论。** 绝对 kcal/mol 不能与 Vina 比（§3.1），这一条没有变。
变的是：§3.2 曾经让「一对姿势之间氢键贡献的差异不可信」，因为决定差异的那些
跨元素氢键根本没被算进去——**这一条不再成立**。

## 4. 明确的实现取舍

这些都是**有意的**决定，写在这里以免被误当成 bug。推导见 `SCORING.md`。

| 取舍 | 后果 |
|---|---|
| 每元素 XS 半径而非统一常数 | 修掉了「同一元素内氢键项恒为零」这个缺陷，跨元素的那一半是网格侧的分块问题，**也已修复**（见 §3.2）。另外这些常数**未与 Vina 交叉验证**（见 §3.1） |
| 4 个网格 slot 而非 Vina 的 3 个 | 内存 +33%（每点多一个 `f32`，4/3），换来消除 donor–donor 伪氢键。**注意**：拆成两张图本身并不保证分解精确——网格曾按元素分块，这是与拆槽无关的另一个成因，已修复（§3.2） |
| hb / hyd 用 C¹ smoothstep 而非硬截断 | 与 Vina 的势**不完全相同**。`hyd` 相对 Vina 的分段线性版本偏保守：`hyd = 1` 的饱和区是 `d ≤ 0.5`，即 C···C 的 **≤ 4.30 Å**，过渡带 4.30–5.30 Å。**本节原先写的「最强疏水吸引落在 1.3–2.3 Å」是错的，且那一段落在碰撞区里面**（3.00 Å 处实测 `+0.514`） |
| 网格梯度不含径向导数项 | 梯度在 cell 边界不连续（C⁰ 插值的固有性质）：**值连续，单侧导数跳**。实测返回姿势**有一个原子落在 cell 面附近**（可复算的三个姿势里，`face-gap` 是 `0.000000 / 0.000056 / 0.000000` cells——**第二个并不在面上**）。**上一版这一行接着写的是「沿任一方向都走不动能量，它们是真极小点」——这句话被实测推翻**：沿 −∇E 的下降量与步长**严格成正比**（斜率 = 位姿自己的 ‖grad‖₂，相对偏差 `2.2e-06`，保持到 δ = 1e-9），所以这些位姿**不是**插值场的极小点，`\|grad\|` 大也不只是因为坐在面上。**线搜索仍然必要**（梯度模长无法区分「面上的拐点」与「真的一阶下降」），但**它的结论只在自己的最小步长处成立**：四个位姿的下降区宽度实测 `1e-08`–`1e-06` conf 单位，被最小步长 `1e-4` **整个跨过**，于是报 `0.00e+00`。审计现在打印 8 步阶梯与下降区宽度，`0.00e+00` 与「那里没有下降」不再是同一句话。完整测量与引擎侧的契约见 §4.2 |
| 分子内项直接对求和，不用临时配体网格 | 相对 Vina 更精确，但每步多几十次求值。**另有一处不一致**：分子内项按 `kind` 判断供受体（`search/mod.rs:152`），所以跨元素氢键在分子内成立；分子间走网格、按元素分块，跨元素不成立。**总能量的两半对「什么是一个氢键」用的不是同一套定义**（见 §3.2） |
| 叔胺标为 `NA` 而非 Meeko/AD 惯例的 `N` | 与旧工具生成的 PDBQT 语义不同。**需要旧惯例时直接改 PDBQT 原子类型即可** |
| 非极性氢在预处理时合并 | 丢失非极性氢的**全部**贡献——形状项与疏水项一起丢，不只是范德华。「对打分影响小」是估计，本轮**没有实测**（需要与非极性氢全展开的同一配体对照对接，本轮未做）。确定影响的是 RMSD 聚类的自由度 |
| 报告前过滤重叠姿势（`min_contact_distance` = 2.0 Å） | 现在是**安全网而不是补丁**——排斥项自己能工作了。副作用：回退时会破坏"提高 exhaustiveness 不会变差"的单调性（见 §6.1） |

### 4.1 碰撞过滤器的已知副作用

`DockingConfig::min_contact_distance` 会在聚类前把不可能的姿势分出去。
正常情况下它**几乎不触发**（实测：14–20 Å 盒、`exhaustiveness` 从 1 到 32，
`rejected_pose_count` 恒为 0）。

> **这一条本轮重跑确认，可以离线复现**：布洛芬对 `examples/rec_prep.pdbqt`，
> 14 Å 与 20 Å 盒各跑 `exhaustiveness` = 1, 2, 4, 8, 16, 32，`seed=42`，
> 12 次运行的 `rejected_pose_count` **全为 0**、`num_poses` 全为 9。
> 附带一条文档原先没写的观察：**这 12 次的 `best_energy` 完全相同**
> （14 Å 盒恒为 `−5.000600`，20 Å 盒恒为 `−4.994040`），即在这个夹具上
> `exhaustiveness` 从 1 到 32 **没有改变结果**。这不能推广成
> 「提高 exhaustiveness 无用」——它只说明这一个夹具上的搜索在 `e = 1`
> 就已经收敛到同一个模态。

但如果搜索确实一个干净姿势都找不到，引擎会**回退**去报告最好的那几个并显式计数
（`DockingResult::rejected_pose_count` + `summary()` 里的 `WARNING`）。
不这么做会把"搜索偏弱"变成"对接失败"。

代价是：**回退时，低 exhaustiveness 的结果可能报告一个比它本该报告的更差的数字**，
因为干净姿势被丢掉了。对应的测试因此改成在前提成立时断言
（先检查 `rejected_pose_count == 0` 再比能量），而不是无条件断言单调。

### 4.2 返回的位姿**不是**插值场的驻点——这是引擎对外承诺与实际行为之间最大的一处落差

`examples/audit_poses.py` 现在把下降量打成**八步阶梯**（步长 `1e-9 … 1.0` conf 单位，
沿归一化的 `−∇E`），每个位姿一行一个台阶。实测结论有三条，全部可复现：

| 台阶 | 实测（生物素 × crambin，18 Å 盒 @ 0.375 Å，`seed=20260929`） |
|---|---|
| `1e-9`（最细） | 下降量 ÷ 步长 = 该位姿自己的 ‖grad‖₂，相对偏差 `2.2e-06`（f64 在这个步长上的噪声底） |
| `1e-4`（旧审计的探测步长） | 位姿 3 报 `+1.52e-04`，其余四个报 `0.00e+00` |
| `1.0`（最粗） | 五个位姿**全部**能量上升（`−3.42 … −82.61` kcal/mol），即已离开盆地 |

**能说的大约是：**位姿在自己的 cell 内是极小的（搜索的 Armijo 充分下降检验保证这一点），
而**任何比线搜索最小步长更窄的下降区，线搜索看不见**。四个「0.00e+00」的下降区宽度实测为
`1.0e-08 / 1.0e-06 / 1.0e-08 / 1.0e-06` conf 单位，位姿 3 是 `3.2e-04`——**旧审计报的
那个 1.52e-04 只是因为它的下降区恰好比 `1e-4` 宽**，不是位姿质量的差别。
`face-gap` 列按 4 位小数打印，区分不了 `1e-08` 与 `3e-04`，所以那一列的分裂是**关于探针的**。

**不能说的大约是：**这些位姿**不是**极小点。实测 `|grad|2` 落在 `4.136 … 11.930`
kcal/mol 每个构象单位，而优化器自己声明的收敛容差
`LbfgsConfig::gradient_tolerance` 是 **1e-4**——**高了四个数量级**。
`examples_check.py` 把这个差距**从下方**钉住（断言 ≥ 1e3×），所以：
引擎哪天真的收敛了，门禁会红，而那句文档措辞必须由人主动改，而不是有人放松一个阈值。

> **契约（建议措辞，需要 `VERIFICATION.md` 的所有者同意后同步）**：
> **本引擎返回的位姿是「在搜索的线搜索分辨率内无下降」的局部极小点，不是插值场的驻点。**
> 这个「分辨率」有具体数字：线搜索的步长在失败时折半，**折到 `1e-12` 构象单位以下就停**
> （`lbfgs.rs::line_search`，至多 40 次折半，Armijo 常数 `1e-4`），所以比 `1e-12` 更窄的
> 下降区它**看不见**；审计自己的阶梯最细只到 `1e-9`（`audit_poses.py::_LINE_SEARCH_STEPS`），
> 比那还窄的，两边都没有仪器。
> 读 `poses.pdbqt` 时应当知道：下降量与步长严格成正比，斜率就是位姿自己的 ‖grad‖₂。

**代价：**报告的能量是可信的（它就是插值场在该点的值），报告的位姿**不是**收敛的局部极小点。
要把契约收紧成「返回前真正收敛」，需要改 `dock-core`（L-BFGS 的收敛判据或
`gradient_tolerance` 的可达性），**不在本轮范围内**；`VERIFICATION.md` 里作为新缺陷登记。

### 4.3 三处「有意的粗糙」，各自的边界写在别处

本节记的是**已知且有意**的三处，它们各自在别处都有推导；这里只记边界，因为
「知道有代价」和「知道代价在哪一层」是两件事。

| 事项 | 代价 | 边界写在 |
|---|---|---|
| **cartoon 的螺旋不区分亚型** | 3-10、α、π 螺旋都按 **3.6 残基/圈**画，所以一段 3-10 螺旋**画得略微欠扭** | 本节下面 |
| **逐项能量分解只有 CPU 路径** | Python 侧**一半问不到**：`backend` 已在分解结果里，但 `TermMaps` 仍不暴露 `BACKEND`，所以「建表之前要不要建」这个更贵的问题（1.5× 内存）问不到 | [`SCORING.md` §5.4](SCORING.md) |
| **返回位姿不是插值场的驻点** | 读 `poses.pdbqt` 的人必须知道契约的分辨率 | 本节 §4.2 |

**cartoon：分类器只说「是螺旋」，不说哪一种。** 二级结构分类器把
α、3-10、π **一律**报成 `helix`（`structure.py`），而
`cartoon_geometry.py::RESIDUES_PER_TURN` 是一个模块级常数 `3.6`，
即 α 螺旋的圈数。按 run 选速率需要一个**逐残基的螺旋亚型**，而分类器不产出它。
所以：**3-10 螺旋（3.0 残基/圈）被画成 3.6 残基/圈，略微欠扭**；
π 螺旋（4.0）则略微过扭。这是**画法**的偏差，**不是几何**的偏差——
骨架坐标没动，受体能量没动，只有缎带的横截面转得不对。

它有办法修而没修，是因为修它需要一个分类器目前不输出的量，而那个量本身
需要另一套判据（H 键几何 + 螺距），那是另一个检查脚本的事。
`scripts/representation_cartoon_check.py` 量的是**画出来的东西**，
`scripts/docs_claims_check.py` 量的是**本文这句话与那个常数是否还一致**。

## 5. 化学处理的边界

**Rust 侧不做任何化学推理。** `dock-core` 相信调用方给的表在化学上是对的。

因此下列工作**必须**由 RDKit（Python 前端）完成，绕过它直接喂
`Ligand::from_arrays` 会得到静默错误的结果：

- 芳香性判定
- 质子化状态
- 电荷赋值
- 显式极性氢的增删

一个具体的例子：如果你绕过 `opendocking.prep` 直接把 RDKit 分子（**带隐式氢**）
的坐标传进引擎，所有羟基氧的 `GetTotalNumHs() == 0`，
于是**没有任何原子被标为 donor**。引擎照常输出结果，只是每个氢键都算错了。
`VERIFICATION.md` §3 的第 7/8/9 条就是这一类 bug 的实例。

其他边界：

- **不处理互变异构体**。只按输入文件里那一个形式。无氢文件里的 His 默认按 HID
  （NE2 上带氢）；文件自带氢时用文件里的。
- **不预测质子化状态**。生理 pH 下的酸碱平衡在输入里怎么写就算怎么用。
- **不处理共价配体、金属配位、大环应变**。
- **受体不建模水分子**。`--keep-waters` 只是保留已有的水，不是预测水合位点。
- **N 端胺基可能只落 1 个氢**而不是 2 个——这是 RDKit `AddHs` 的几何摆放限制，
  不是化学判断错误。实测 crambin 的 N 端就是这种情况（55 个供体位点全覆盖，
  唯独 N 端少一个氢）。影响 N 端盐桥强度，不影响功能。

### 5.1 外来 PDBQT 的原子类型：只有一半的 token 会被识别

分类以 PDBQT 类型列为权威（`SCORING.md` §7），而氢键能力只在
`ND / NDA / OD / ODA`（供）与 `NA / NDA / OA / ODA`（受）里成立。
**实测落到 `Other`（既不供也不受、只剩形状项）的 token 包括 `N`、`NS`、
`O`、`OS`、`S`、`SA`、`P`。**

后果是具体的：**Meeko / AutoDock 4 惯例写的 `N`（中性胺氮）和 `SA`（硫醚硫）
在本引擎里不参与氢键项**，只贡献排斥与高斯形状。一个用旧工具准备的、
含硫醚或叔胺的配体，所有氢键能量都是 0，而引擎**不会报错**。
本项目自己的 `prepare_ligand` 写的是 `NA` + 显式 `HD`，所以 `examples/`
里的夹具不受影响；**风险只在导入第三方 PDBQT 时出现**。
绕法是把类型列改成受体的 token，或用 `opendocking.prep` 重新制备。

另有一个往返损失：三字符类型 `NDA` / `ODA` 读不出来（类型列只取两列，
写出时也被截成两字符），所以「既供又受」的原子只能靠「受体 token + 显式
`HD`」表达。<!-- DEFECT -->

**这一节的后果比上面写的更重一层。** 落到 `Other` 的原子**仍然有形状项**——
但只有当受体里存在同元素的原子时。网格按元素分块（§3.2），所以一个 `N` 原子
配上一个不含氮的受体时，它对总能量的贡献是**精确 0.000000**：
既没有氢键，也没有排斥，也没有高斯形状。上面这段说「只贡献排斥与高斯形状」，
在受体含该元素时是对的；受体不含时是**什么都不贡献**，而且引擎不报错、不警告。
实测：`examples/rec_prep.pdbqt`（`OA`×12 + `C`×12 + `HD`×6，无 N 无 S）对
配体 token `N` / `ND` / `NA` / `S` 一律给 `+0.000000`。

## 6. 性能与规模

- **网格内存是硬约束**。实测（`estimate_memory_mb`，40 个 `f32`/点）：

  | 立方体边长 | @ 0.375 Å | @ 0.1875 Å | @ 0.75 Å |
  |---|---|---|---|
  | 14 Å | 9.05 MB | 66.98 MB | 1.22 MB |
  | 20 Å | **25.39 MB** | 192.22 MB | 3.35 MB |
  | 40 Å | **192.22 MB** | 1516.48 MB | 25.39 MB |

  上一版写的是「20 Å = 25 MB；40 Å ≈ 600 MB」。**20 Å 那条对，40 Å 那条错了
  一个量级方向上的三倍**（192 MB，不是 600 MB）——按 40 Å 写的估算会让人以为
  比实际需要的更多，而这个方向的错误正是让人不信任工具的那一种。
  **`spacing` 减半是 ×7.6 而不是 ×8**：20 Å 盒上 25.39 → 192.22 MB。差的那 4%
  是网格点数向上取整的余数（`(side/spacing + 1)` 不是纯粹的 `1/spacing` 比例），
  小盒子偏多、大盒子趋近 8。

  上限是 `MAX_GRID_POINTS = 2^28` = 40.0 GiB，**超了在分配之前**报错并告诉你
  需要多少 MB（实测 400 Å 立方 @ 0.375 Å：「needs at least 185880 MB of grid;
  the limit is ... points (40960 MB)」）。所以
  `receptor.estimate_memory_mb(box_, spacing)` 应该在分配之前调用，
  而不是等它抛错。
- **盒子必须装得下配体，但这条检查在 `dock()` 里，不在 `precalculate()` 里。**
  `monte_carlo.rs:114` 的判据是 `needed = 2 × ligand.radius() + 1.0` Å，
  逐轴与盒子边长比较，任何一边小于它就拒绝并报出实际需要多少。
  **上一版这里写"实测布洛芬 16 原子需要 11.1 Å"——那是 `2 × radius`，
  漏掉了公式末尾的 `+1.0`。实测布洛芬 `radius = 5.536`，
  需要 `2 × 5.536 + 1 = 12.07 Å`，引擎报的是 12.1 Å。**
  两个由此而来的、上一版没写的后果：
  * **网格先分配、尺寸后检查。** 一个 4 Å 的盒子 `precalculate` 照常成功
    （**本轮实测 `dims = (12, 12, 12)`、`memory_mb = 0.2637`，内存已经花掉**），
    要到 `dock()` 才告诉你盒子太小：
    `invalid parameter 'grid box' = [4.0, 4.0, 4.0]: axis x is 4.0 Å but the
    ligand needs at least 12.1 Å`。
    **上一版这里写 `dims = (6,6,6)`，是错的**——4 Å / 0.375 Å = 10.67，
    格点数是 `ceil(4 / 0.375) + 1 = 12`。判断「格子太少」的经验值因此也不成立。
    所以 `receptor.estimate_memory_mb(box_, spacing)` 要在 `precalculate`
    **之前**调用——它能省掉一整次分配，但省不掉这次检查。
  * **判据用的是标量 `radius`，不是逐轴的包围盒。** 一个又长又扁的盒子
    （例如 30 × 8 × 8 Å 放一个长链配体）会被拒绝，哪怕配体在那个方向上放得下。
    这是有意保守还是图省事，代码里没写。
- **`radius` 是质心到最远原子的距离**（`Ligand.radius`），不是直径。
  `needed` 里的 `2 × radius` 才是直径那一项，再加 1 Å 的表面距离余量。
- **搜索成本近似线性于 `exhaustiveness`**。`-e 8` 与 `-e 32` 差 4 倍时间，
  收益不线性。
- **多线程只加在预制表和轨迹级**。L-BFGS 内层是严格串行的，
  所以超过物理核心数后收益递减。
- **GPU 只加速批量原子-网格求值**，不加速 L-BFGS 的下降步，
  也不加速网格预制表。对单条轨迹的小配体，加速比有限。
  GPU 端用 `f32` 累加，所以 `use_gpu` **默认是 False**。
  **两处对"差多少"的写法不一致，且本轮无法核实**：`core.py` 的
  `evaluate_conformation` docstring 说相对误差"量级 1e-7"，本文件原来写
  "~1e-6"。本机 `gpu_status()` 返回 `{'compiled': False, 'available': False}`，
  没有任何 GPU 路径可跑，**两个数字都没有在本地复算过**。
  单测 `gpu_energies_match_the_cpu_interpolation` 断言的是差 < 1e-3，
  比这两个说法宽三个数量级，因此它也定不了这个数。<!-- DEFECT -->
- **没有实测吞吐量数字**。`cargo bench -p dock-core` 可以跑，但本仓库的
  `VERIFICATION.md` 不引用任何 benchmark 结果，因为写它的时候没跑过。

> **本节表格与 §7 的行号引用是有检查的**：`scripts/docs_claims_check.py`
> 把本文的数字**解析出来**（不是另抄一份）再和引擎、`types.rs` / `grid.rs` /
> `scoring.rs` / `prep.py` 的实际值比对，共 56 项。它刻意**不**持有任何转录常量——
> 那正是 `scoring_cross_check.py` 的 `WEIGHTS` / `XS_RADIUS` 做的事，
> 结果是引擎与那个副本一致，而副本与本文档是否一致**无人断言**。
> 这个文件补的就是那个缺口。
>
> 它的容差也经过双向变异证明：**36 个变异（23 个改本文、13 个改 Rust 源码）
> 全部使检查变红，0 个存活**，改动后逐字节校验文件已还原。
> 其中一次变异暴露了检查自身的一个真实弱点：内存表的容差原为 `0.01 MB`，
> 而发布值只有两位小数，于是 `1.23` 对上真值 `1.2207`（差 `0.0093`）会漏过去；
> 现已收紧到 `0.005`。**已发布的数字若与实测差在半个末位以内，视为一致——
> 这条边界是明确的，不是含糊的。**

## 7. 输入格式的边界

- **PDBQT 解析是 clean-room 实现**，依据公开发布的列格式规范。
  对规范的实现是完整的，但它**没有**做过与 AutoDock 4 / Meeko 产出的
  PDBQT 的往返一致性测试。
- **写出的 `.map` 文件不是 `maps.C.map` / `maps.OA.map`。** 上一版这么写，
  **实测是错的**。`write_map_files` 实际产出 **40 个**文件，命名是
  「元素符号 + slot 后缀」，`C`/`O`/`N`/`S`/`P`/`F`/`Cl`/`Br`/`I`/`Met`
  各四个：

  ```
  maps.Ce.map  maps.Chbdon.map  maps.Chbacc.map  maps.Chyd.map
  maps.Oe.map  maps.Ohbdon.map  maps.Ohbacc.map  maps.Ohyd.map
  … 每个 10 个元素各 4 个，共 40 个
  ```

  也就是说命名是**本项目自己的**（按 §3.2 的元素×slot 布局），不是 AutoDock 4
  那种按配体原子类型的 `maps.C.map` / `maps.OA.map` / `maps.HD.map`。
  两者**不能互相读**：AutoDock 4 的一个类型对应一张图，这里一个元素对应四张图。
  **这些文件没有验证过能被 AutoDock 4 读回，也不该指望它能。**<!-- DEFECT -->
- **受体准备**（`prep-receptor`）不做侧链优化、不做质子化状态预测、
  不做电荷指派（受体本来就只用形状与极性）。
- **配体准备**用 RDKit 的 ETKDGv3 + MMFF 优化三维构象，固定随机种子
  **`0xF00D`**（`prep.py:362`，`AllChem.EmbedMolecule(mol, randomSeed=0xF00D)`，
  之后 `MMFFOptimizeMolecule(mol, maxIters=500)`）。
  **上一版把种子写成 `0x0D0C`，那是错的**——同一个数字的两种读法，不是同
  一个常量；照着 `0x0D0C` 去复现会得到另一个构象。<!-- DEFECT -->

## 8. 不适合的用途

明确说一下，避免误用：

- ❌ **临床决策**。经验打分函数没有任何临床验证。
- ❌ **代替实验**。它预测的是姿势，不是亲和力。
- ❌ **虚拟筛选的大规模吞吐**。没有批处理调度、没有 FEP、没有打分函数集成。
- ❌ **蛋白-蛋白对接**。没有刚体对接（rigid docking）路径，只有柔性配体对固定受体。
- ❌ **核酸 / 糖类配体**。没有针对它们重拟合的原子类型或参数。
- ✅ **小分子柔性配体对已制备好的小盒子**，作为初筛与可视化工具。
