# 已知限制

本工具是什么、以及**明确不是什么**。这份文档的用途是让你在提交到一篇论文之前
先读完，避免"能量是负的所以结果是对的"这类误判。

相关：[`VERIFICATION.md`](VERIFICATION.md)（实际跑了什么）、
[`SCORING.md`](SCORING.md)（算法细节与偏离）。

---

## 1. 最要紧的一条

**本工具目前不是一个被验证过能正确预测结合姿势的工具。**

它是一个结构完整、单元测试覆盖到数值正确性、GPU 与 CPU 数值一致、
但**尚未与 AutoDock Vina 做交叉数值比对**的引擎。

具体来说，以下问题还没有证据：

- 预测能量与 Vina 差多少（**没有交叉数值比对**，见 §3.1）；
- RMSD 聚类阈值在实际数据上是否合适；
- **盲视对接**能不能自己找对口袋（回对接用的是已知位点盒，见 §2.1）。

「pose 落在正确口袋」这一条**部分**有了证据（回对接基准），不再是完全空白。

如果你的用途是**筛选**（这个配体值不值得进一步研究），风险可控。
如果用途是**结构假设**（这个配体是怎么结合的），请先用 Vina 跑一遍做交叉验证。

## 2. 验证覆盖的边界

| 维度 | 状态 |
|---|---|
| 平台 | 只在 Windows 11 x86_64 验证。macOS (Metal) / Linux (Vulkan) **未测** |
| GPU | 只在 NVIDIA RTX 3050 Laptop 验证。AMD 独显 / Intel 核显 / Apple Silicon **未测** |
| 受体 | 真实蛋白测过 **crambin (1CRN, 46 残基)**，以及回对接基准里的 8 个结构（1HVR、3PTB 等，见 `VERIFICATION.md` §3.7）。**盲视对接没有验证** |
| 配体 | 小分子（苯、甲苯、苯酚、布洛芬、生物素、沙丁胺醇），**没有肽段、核酸、金属配合物** |
| 对接 | 回对接跑的是 39 × 26 × 41 Å 级的口袋盒与 `exhaustiveness` 8–128。**没有系统的大盒子 / 高 throughput 数据** |
| GUI | 渲染层与交互控件用真实 Qt 事件验证，脚本是 `workbench_interaction_check.py`。**上一版写的"44 项"已过期**：该文件现有 193 个 `check(` 调用点、21 个 `section(`。**本轮未能取得实际执行条数**——这台机器没有 OpenGL 上下文（`workbench_smoke` 以 `no Qt GL context` 结束），所以这里给出的是静态计数，不是跑出来的数字。**未测**：多显示器 / 混合 DPI 缩放、触屏与三键鼠标以外的输入设备、窗口在后台时长时间运行的稳定性 |

### 2.1 回对接：跑过了，但**本文件上一版说它没跑过，那是错的**

上一版这里写「**本工具从未被验证过能把一个已知结合的配体放回它的口袋**」。
这句话现在是**假的**，而且属于最坏的一种错：一个已经不再成立的限制会让读者
主动放弃一个本来能用的工具，所以它比漏写限制更糟。

实际情况：

* `scripts/redock_benchmark.py` 就是这个验证，结果记在
  [`VERIFICATION.md`](VERIFICATION.md) §3.7 与其中的基准表里。
  `opendocking.core.exhaustiveness_for_box` 的 docstring 里那句
  「3PTB 位点盒 39 × 26 × 41 Å，exhaustiveness 16 → 12.88 Å RMSD，
  64 → 1.26 Å」就是从这里来的。
* 它**不是 CI 门禁**，因为它要联网取结构、每个案例都跑一次真实搜索。
  本轮**无法离线复现**：需要从 RCSB 下载，本机出网被拦。所以下面这些数字
  我只能转述，不能核对。

**仍然成立、且不要因为上面那句被撤销而忽略的：**

* **"能量函数是合理的"仍然只是间接证据。** 回对接测的是「搜索能不能找回一个
  已知构象」，它同时经过打分函数和搜索两层，任何一层坏掉都可能互相掩盖。
* **输入本身有已知缺陷，所以那些数字是下限而不是测量值。**
  `redock_benchmark.py` 自己的 docstring 写明：晶体结构里的配体不带键，
  脚本按原子间距推断连接性，这会**把芳香性和形式电荷弄错**，从而同时改变
  可旋转键集合和部分电荷。
* **绝对 kcal/mol 仍然不能和 Vina 或文献比较**（见 §3.1），这条没有因为
  回对接跑过而放松半分。
* **多构象盲视（blind docking）没有验证。** 回对接用的是已知的结合位点盒，
  「不知道位点在哪」这个更难的问题依然没有证据。

## 3. 经验打分函数本身的限制

这不是本工具独有的问题，但使用者必须知道。

- **经验打分函数的姿势预测能力有限**。Vina 打分函数在它自己论文的基准集上，
  正确姿势的判别成功率明显低于 100%（原文报告的数量级在 60% 附近，
  以 ROCS 指标衡量）。
  **注意：这个数字本仓库没有重新核实过**，写在这里只是提醒量级，
  不是引用来论证。本工具复现的是 Vina 的**势函数**，不是它的预测能力。
  它是筛选工具，不是判决工具。
- **只有短程项，没有显式静电项**。带电配体、带电口袋（Asp/Glu/Lys/Arg）体系的
  打分误差会明显变大。Vina 1.2 也有同样的问题。
- **没有溶剂化项**。埋藏与暴露的区分是间接的、粗糙的。
- **没有扭转熵项**。柔性配体的打分会偏好展开构象。
- **Vinardo 的重参数化是否复现正确，未经验证**（见 §1）。

### 3.1 相互作用半径没有与 Vina 交叉验证

本轮修掉了一个真实缺陷：所有重原子的相互作用半径曾经统一取 0.4 Å，
导致氢键项在任何真实氢键距离上恒为零、全部吸引项落进碰撞区
（细节见 [`SCORING.md` §1.1](SCORING.md)）。修法是改用每元素的 XS 半径。

**但这些常数是按参考非键接触距离取的，没有与 AutoDock Vina 的二进制比对过。**
因此：

* 本工具输出的**绝对 kcal/mol 数字不应**与 Vina 输出或文献值直接比较；
* 相对排序、pose 质量、几何合理性都可以用，绝对亲和力不可以。

`docs/VERIFICATION.md` §1 记录了这个阻塞项的具体原因（出网被拦，装不了 `vina` 包）。

## 4. 明确的实现取舍

这些都是**有意的**决定，写在这里以免被误当成 bug。推导见 `SCORING.md`。

| 取舍 | 后果 |
|---|---|
| 每元素 XS 半径而非统一常数 | 修掉了"氢键项恒为零"的缺陷，但**未与 Vina 交叉验证**（见 §3.1） |
| 4 个网格 slot 而非 Vina 的 3 个 | 内存 +33%（每点多一个 `f32`），换来消除 donor–donor 伪氢键 |
| hb / hyd 用 C¹ smoothstep 而非硬截断 | 与 Vina 的势**不完全相同**。`hyd` 的窗口相对 Vina 的分段线性版本偏保守，最强疏水吸引落在 C···C 的 1.3–2.3 Å |
| 网格梯度不含径向导数项 | 梯度在 cell 边界不连续（C⁰ 插值的固有性质）。**实测每个返回姿势都有原子正好坐在 cell 面上**，于是 `\|grad\|` 看起来很大（2.3–5.9）且与中心差分符号相反——但沿任一方向都走不动能量，它们是真极小点。判断收敛要看线搜索，不能看梯度模长 |
| 分子内项直接对求和，不用临时配体网格 | 比 Vina 精确，但每步多几十次求值 |
| 叔胺标为 `NA` 而非 Meeko/AD 惯例的 `N` | 与旧工具生成的 PDBQT 语义不同。**需要旧惯例时直接改 PDBQT 原子类型即可** |
| 非极性氢在预处理时合并 | 丢失非极性氢的范德华贡献。对打分影响小，但会影响 RMSD 聚类的自由度 |
| 报告前过滤重叠姿势（`min_contact_distance` = 2.0 Å） | 现在是**安全网而不是补丁**——排斥项自己能工作了。副作用：回退时会破坏"提高 exhaustiveness 不会变差"的单调性（见 §6.1） |

### 4.1 碰撞过滤器的已知副作用

`DockingConfig::min_contact_distance` 会在聚类前把不可能的姿势分出去。
正常情况下它**几乎不触发**（实测：14–20 Å 盒、`exhaustiveness` 从 1 到 32，
`rejected_pose_count` 恒为 0）。

但如果搜索确实一个干净姿势都找不到，引擎会**回退**去报告最好的那几个并显式计数
（`DockingResult::rejected_pose_count` + `summary()` 里的 `WARNING`）。
不这么做会把"搜索偏弱"变成"对接失败"。

代价是：**回退时，低 exhaustiveness 的结果可能报告一个比它本该报告的更差的数字**，
因为干净姿势被丢掉了。对应的测试因此改成在前提成立时断言
（先检查 `rejected_pose_count == 0` 再比能量），而不是无条件断言单调。

## 5. 化学处理的边界

**Rust 侧不做任何化学推理。** `dock-core` 相信调用方给的表在化学上是对的。

因此下列工作**必须**由 RDKit（Python 前端）完成，绕过它直接喂
`Ligand::from_arrays` 会得到静默错误的结果：

- 芳香性判定
- 质子化状态
- 电荷赋值
- 显式极性氢的增删

一个具体的例子：如果你绕过 `opendocking.prep` 直接把 RDKit 分子（**带隐式氢**）
的坐标传进引擎，所有羟基氧的 `GetTotalNumHs() == 0`，
于是**没有任何原子被标为 donor**。引擎照常输出结果，只是每个氢键都算错了。
`VERIFICATION.md` §3 的第 7/8/9 条就是这一类 bug 的实例。

其他边界：

- **不处理互变异构体**。只按输入文件里那一个形式。无氢文件里的 His 默认按 HID
  （NE2 上带氢）；文件自带氢时用文件里的。
- **不预测质子化状态**。生理 pH 下的酸碱平衡在输入里怎么写就算怎么用。
- **不处理共价配体、金属配位、大环应变**。
- **受体不建模水分子**。`--keep-waters` 只是保留已有的水，不是预测水合位点。
- **N 端胺基可能只落 1 个氢**而不是 2 个——这是 RDKit `AddHs` 的几何摆放限制，
  不是化学判断错误。实测 crambin 的 N 端就是这种情况（55 个供体位点全覆盖，
  唯独 N 端少一个氢）。影响 N 端盐桥强度，不影响功能。

### 5.1 外来 PDBQT 的原子类型：只有一半的 token 会被识别

分类以 PDBQT 类型列为权威（`SCORING.md` §7），而氢键能力只在
`ND / NDA / OD / ODA`（供）与 `NA / NDA / OA / ODA`（受）里成立。
**实测落到 `Other`（既不供也不受、只剩形状项）的 token 包括 `N`、`NS`、
`O`、`OS`、`S`、`SA`、`P`。**

后果是具体的：**Meeko / AutoDock 4 惯例写的 `N`（中性胺氮）和 `SA`（硫醚硫）
在本引擎里不参与氢键项**，只贡献排斥与高斯形状。一个用旧工具准备的、
含硫醚或叔胺的配体，所有氢键能量都是 0，而引擎**不会报错**。
本项目自己的 `prepare_ligand` 写的是 `NA` + 显式 `HD`，所以 `examples/`
里的夹具不受影响；**风险只在导入第三方 PDBQT 时出现**。
绕法是把类型列改成受体的 token，或用 `opendocking.prep` 重新制备。

另有一个往返损失：三字符类型 `NDA` / `ODA` 读不出来（类型列只取两列，
写出时也被截成两字符），所以「既供又受」的原子只能靠「受体 token + 显式
`HD`」表达。<!-- DEFECT -->

## 6. 性能与规模

- **网格内存是硬约束**。实测（`estimate_memory_mb`，40 个 `f32`/点）：

  | 立方体边长 | @ 0.375 Å | @ 0.1875 Å | @ 0.75 Å |
  |---|---|---|---|
  | 14 Å | 9.05 MB | 66.98 MB | 1.22 MB |
  | 20 Å | **25.39 MB** | 192.22 MB | 3.35 MB |
  | 40 Å | **192.22 MB** | 1516.48 MB | 25.39 MB |

  上一版写的是「20 Å = 25 MB；40 Å ≈ 600 MB」。**20 Å 那条对，40 Å 那条错了
  一个量级方向上的三倍**（192 MB，不是 600 MB）——按 40 Å 写的估算会让人以为
  比实际需要的更多，而这个方向的错误正是让人不信任工具的那一种。
  **`spacing` 减半是 ×7.6 而不是 ×8**：20 Å 盒上 25.39 → 192.22 MB。差的那 4%
  是网格点数向上取整的余数（`(side/spacing + 1)` 不是纯粹的 `1/spacing` 比例），
  小盒子偏多、大盒子趋近 8。

  上限是 `MAX_GRID_POINTS = 2^28` = 40.0 GiB，**超了在分配之前**报错并告诉你
  需要多少 MB（实测 400 Å 立方 @ 0.375 Å：「needs at least 185880 MB of grid;
  the limit is ... points (40960 MB)」）。所以
  `receptor.estimate_memory_mb(box_, spacing)` 应该在分配之前调用，
  而不是等它抛错。
- **盒子必须装得下配体，但这条检查在 `dock()` 里，不在 `precalculate()` 里。**
  `monte_carlo.rs:114` 的判据是 `needed = 2 × ligand.radius() + 1.0` Å，
  逐轴与盒子边长比较，任何一边小于它就拒绝并报出实际需要多少。
  **上一版这里写"实测布洛芬 16 原子需要 11.1 Å"——那是 `2 × radius`，
  漏掉了公式末尾的 `+1.0`。实测布洛芬 `radius = 5.536`，
  需要 `2 × 5.536 + 1 = 12.07 Å`，引擎报的是 12.1 Å。**
  两个由此而来的、上一版没写的后果：
  * **网格先分配、尺寸后检查。** 一个 4 Å 的盒子 `precalculate` 照常成功
    （`dims = (6,6,6)`，内存已经花掉），要到 `dock()` 才告诉你盒子太小。
    所以 `receptor.estimate_memory_mb(box_, spacing)` 要在 `precalculate`
    **之前**调用——它能省掉一整次分配，但省不掉这次检查。
  * **判据用的是标量 `radius`，不是逐轴的包围盒。** 一个又长又扁的盒子
    （例如 30 × 8 × 8 Å 放一个长链配体）会被拒绝，哪怕配体在那个方向上放得下。
    这是有意保守还是图省事，代码里没写。
- **`radius` 是质心到最远原子的距离**（`Ligand.radius`），不是直径。
  `needed` 里的 `2 × radius` 才是直径那一项，再加 1 Å 的表面距离余量。
- **搜索成本近似线性于 `exhaustiveness`**。`-e 8` 与 `-e 32` 差 4 倍时间，
  收益不线性。
- **多线程只加在预制表和轨迹级**。L-BFGS 内层是严格串行的，
  所以超过物理核心数后收益递减。
- **GPU 只加速批量原子-网格求值**，不加速 L-BFGS 的下降步，
  也不加速网格预制表。对单条轨迹的小配体，加速比有限。
  GPU 端用 `f32` 累加，所以 `use_gpu` **默认是 False**。
  **两处对"差多少"的写法不一致，且本轮无法核实**：`core.py` 的
  `evaluate_conformation` docstring 说相对误差"量级 1e-7"，本文件原来写
  "~1e-6"。本机 `gpu_status()` 返回 `{'compiled': False, 'available': False}`，
  没有任何 GPU 路径可跑，**两个数字都没有在本地复算过**。
  单测 `gpu_energies_match_the_cpu_interpolation` 断言的是差 < 1e-3，
  比这两个说法宽三个数量级，因此它也定不了这个数。<!-- DEFECT -->
- **没有实测吞吐量数字**。`cargo bench -p dock-core` 可以跑，但本仓库的
  `VERIFICATION.md` 不引用任何 benchmark 结果，因为写它的时候没跑过。

## 7. 输入格式的边界

- **PDBQT 解析是 clean-room 实现**，依据公开发布的列格式规范。
  对规范的实现是完整的，但它**没有**做过与 AutoDock 4 / Meeko 产出的
  PDBQT 的往返一致性测试。
- **写出的 `.map` 文件**遵循 AutoDock 命名约定
  （`maps.C.map`、`maps.OA.map`），但**没有**验证过能被 AutoDock 4 读回。
- **受体准备**（`prep-receptor`）不做侧链优化、不做质子化状态预测、
  不做电荷指派（受体本来就只用形状与极性）。
- **配体准备**用 RDKit 的 ETKDGv3 + MMFF 优化三维构象，固定随机种子
  **`0xF00D`**（`prep.py:362`，`AllChem.EmbedMolecule(mol, randomSeed=0xF00D)`，
  之后 `MMFFOptimizeMolecule(mol, maxIters=500)`）。
  **上一版把种子写成 `0x0D0C`，那是错的**——同一个数字的两种读法，不是同
  一个常量；照着 `0x0D0C` 去复现会得到另一个构象。<!-- DEFECT -->

## 8. 不适合的用途

明确说一下，避免误用：

- ❌ **临床决策**。经验打分函数没有任何临床验证。
- ❌ **代替实验**。它预测的是姿势，不是亲和力。
- ❌ **虚拟筛选的大规模吞吐**。没有批处理调度、没有 FEP、没有打分函数集成。
- ❌ **蛋白-蛋白对接**。没有刚体对接（rigid docking）路径，只有柔性配体对固定受体。
- ❌ **核酸 / 糖类配体**。没有针对它们重拟合的原子类型或参数。
- ✅ **小分子柔性配体对已制备好的小盒子**，作为初筛与可视化工具。
