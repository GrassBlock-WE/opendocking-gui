## 2. 未验证 / 未完成

**这一节是本文的重点。**

### 2.1 与 AutoDock Vina 的数值比对 —— 未做

**没有**用 Vina 跑同一个配体/受体再比对 pose 与能量。
权重按公开值实现、梯度有有限差分锁定，但"实现是对的"和
"算出来的姿势与 Vina 一样"是两件事。

**这在本轮变得更重要**：本轮修掉的相互作用半径缺陷（§3.2.1）用的
是**按参考非键接触距离取的每元素 XS 半径**，不是从 Vina 抄来的值。
它们让每一项落在物理上正确的距离（这一点由晶体学接触距离独立验证），
但**具体常数和 Vina 用的是否逐位相同，无从确认**。

因此：**本工具输出的绝对 kcal/mol 数字不应与 Vina 输出或文献值直接比较。**
相对排序、姿势质量、几何合理性可以参考。

**未能完成的原因（已核实，不是没试）**：`pip install vina` 失败——
本机 pip 被指向一个已失效的本地代理 `127.0.0.1:7890`，
绕过代理后镜像同样不可达。Python 与 PowerShell 的出网都被拦截，
只有工具层 `web_fetch` 可用，而它无法安装软件包。

### 2.2 回对接（redocking）—— 未做

这是对接质量的金标准：把配体对进它在晶体中的口袋，看能否复现晶体姿势。

**未能完成的原因（已核实）**：拿到了 1STP（streptavidin + 生物素）的完整
配体（16 重原子 + CONECT 键表），但工具层 `web_fetch` 对超过约 16000 token
的响应会**截断中间内容**，而 1STP 的蛋白部分（901 原子）恰好落在被截断的区间。
实际取到的蛋白片段是残基 96–133，距离生物素最近 12 Å——
**口袋壁全在缺失的残基里**，用这个片段做回对接没有意义。

crambin 没有结合口袋，所以它也不能替代一个 holo 结构。

### 3.2 能量函数层面

这一节的**诊断最后被推翻了**，根因在 §3.2.1。保留原过程是因为它记录了
"症状指向错误方向"这件事本身。

| # | 现象 | 当时的结论 |
|---|---|---|
| 17 | 把配体对进 crambin 疏水核心，所有 pose 每个原子都在受体 2 Å 内，最近 0.17–0.71 Å | 见下 |
| 18 | 同样的大盒子、配体可待在表面时，**仍然**全部 clash | 不是"盒子选错"这么简单 |
| 19 | 500 次随机采样：最佳**无冲突**放置 E = −0.010，最佳**有冲突**放置 E = −1.001 | "打分函数本身偏好埋藏" |

**当时的修复**：在聚类**之前**把物理上不可能的姿势分离出去，
优先报告可成立的姿势；一个都找不到时才回退，并**通过
`DockingResult.rejected_pose_count` 与 CLI 的 `WARNING:` 显式告知**。
硬拒绝会把"搜索偏弱"变成"对接失败"，所以没有采用。

**这个修复的副作用，必须说清楚**：碰撞过滤**破坏**了
"提高 exhaustiveness 不会变差"的单调性——当弱搜索只找到碰撞姿势时，
它会回退并报告一个更差的（但诚实的）数字。
`test_higher_exhaustiveness_does_not_worsen` 因此改为在前提成立时断言该性质。

### 3.2.1 根因：所有重原子的相互作用半径是 0.4 Å

**§3.2 的"没有有效排斥"是一个症状，不是原因。** 真因是
`Element::interaction_radius()` 对**所有**重原子返回同一个 `0.4 Å`。
0.4 是共价键长，不是相互作用半径。表面距离是 `d = r − (Rᵢ + Rⱼ)`，
所以 `R` 直接决定每一项落在间距轴的哪个位置：

| 项 | 需要的 `d` | 换算成真实间距 | 合理？ |
|---|---|---|---|
| `hb` | `≤ −0.5` | **0.3 Å**（O···O） | 否 |
| `g1` | `= 0.5` | 1.3 Å（C···C） | 否 |
| `g2` | `= 0` | 0.8 Å（C···C） | 否 |
| `hyd` | `≤ 0.5` | 1.3 Å（C···C） | 否 |

两个氧原子相距 0.3 Å 不是氢键，是一个原子和它自己的镜像。
**权重 −0.587439（Vina 函数里最大的单项）在任何真实氢键能形成的距离上恰好为零。**

**怎么发现的**：冠醚 + 酚的氢键几何明明摆对了（2.0 Å 距离，有单调信号），
但所有配体的能量都是 **−0.000**。把酚羟基从 `OA` 改成 `A` 做对照，
氢键项的贡献只有 **−0.0032 kcal/mol**——应该约 −0.18，差了 35 倍。

**修法**：改用每元素的 XS 半径（C 1.9 / N 1.75 / O 1.6 / S 2.0 Å，H 为 0）。
同时修掉 `hbond_term` 的窗口端点（曾整体偏近 0.5 Å，最大值落在 2.5 Å）。

> **本节两行「H 为 0」与「C···C 最小值 3.00 Å」已被第 171 条证伪/更正。**
> C···H 距离的零点交叉实测在 **3.74 Å**，隐含氢的相互作用半径约 **1.84 Å**，
> 而此处写的是 H 为 0。二者不可能同时成立，且是**本节自己**刚刚换上的半径表。
> 我不猜哪一个是对的——正确修法需要打开 Rust 侧，此处如实标注。

| 对照 | 修前 | 修后 |
|---|---|---|
| O···O 供受体氢键最小值 | 2.0 Å 处 −0.005（=没有） | **2.50 Å 处 −0.177** |
| C···C 疏水最小值 | 2.0 Å 处 −0.005 | **4.30 Å 处 −0.0692**（本行原写「3.00 Å 处 −0.050」，**已证伪，见缺陷 171**） |
| 冠醚 + 苯 | E = −0.00 | **E = −2.05**，最小间距 2.88 Å |
| 冠醚 + 布洛芬 | E = −1.83，最小间距 **0.13 Å**（全 16 原子重叠） | **E = −5.03**，最小间距 **2.64 Å** |
| crambin + 生物素 | E = −2.20，最小间距 **0.54 Å** | **E = −5.04**，最小间距 **2.24 Å** |
| 500 次随机采样的最佳放置 | 无冲突 −0.010 vs 有冲突 −1.001（差 0.99） | **两者都是 −0.815，无冲突占优（差 0.000）** |
| 实心碳晶格 + 苯 | 埋进去是**最便宜**的 | **+289.9 kcal/mol** |

**连带修掉的一个潜伏 bug**：预制表内循环拿**真实距离** `r2` 去做**表面距离**阈值
`cutoff` 的比较，等于把真实截断设成了 `cutoff` 而不是 `cutoff + 2·R`，
高斯项的尾巴一直被削掉一截（0.8 Å → 3.8 Å）。这类错误不会让任何测试变红。

**连带发现并重写的一个坏测试**：`grid::tests::interpolation_is_linear_along_one_axis`
在一个**非线性**的场（高斯 + 排斥）上断言三线性插值是线性的。
它过去只是因为场太平而碰巧通过——修好半径后场变陡，它立刻变红。
现在改成对比**存储的节点值**，测的是插值算子本身，与场无关。

### 3.2.2 一个看起来像梯度 bug、其实不是的现象

生物素对进 crambin 后，返回姿势的 `|grad|` 是 2.3–5.9，
且**逐分量与中心差分符号相反**：

```
dof     analytic    numeric
tx       0.7632    -0.4956
ry       2.2074    -1.4849
tau0    -3.1266    +2.1669
```

第一反应是"扭转梯度算错了"。**不是。** 测姿势到最近 cell 面的距离：

```
pose 1: closest approach to a cell face = 0.0000 cells
```

**每个返回姿势都恰好有一个配体原子坐在网格面上**，于是该点存在两个大小相近、
符号相反的单边梯度，而函数在那里取到极小值（沿两个方向都走不动能量：
起点 −5.222，解析方向最好 −5.209，数值方向 −5.215）。

**解析梯度本身是对的**，两条独立证据：

| 检查 | 结果 |
|---|---|
| 10 组随机在盒内构象 × 11 DOF，解析 vs 中心差分 | 全部 `err = 0.0000` |
| 新增 Rust 测试（butane 1 扭转 + hexane 4 扭转，全 DOF） | 通过 |

**真正缺的是测试覆盖**：`kinematics.rs` 的 `conf_gradient` 有限差分测试喂的是
坐标的线性泛函 `E = Σ gᵢ·rᵢ`，只能证明回代代数对，
证明不了打分管线产出的**原子梯度**对。现已补上
`search::tests::the_analytic_gradient_is_the_gradient_of_the_reported_energy`。

**方法论教训**：沿 −∇E 的线搜索必须**先归一化方向**。
用原始 `∇` 走 `k·∇`，在 `|∇| = 5.9` 时步长 0.05 就把原子挪 0.3 Å、步长 3.2 挪 19 弧度，
中间那段有用的范围根本没采到，于是会误判成"已经是极小点"。

### 3.9 `odgui` 入口点

`odgui` 与 `odcli` 是两个**互相独立**的 console script
（`opendocking.workbench.launcher:main` 与 `opendocking.cli:main`）：
装了工作台不影响 CLI，只装 CLI 也不影响工作台。
启动器不在模块顶层 import Qt / modernGL，
所以 `odgui --help` 与 `odgui --check` 在没有图形栈的机器上也能给出可读的结果，
而不是抛 traceback。

| 检查 | 结果 |
|---|---|
| `odgui --check`（无窗口） | `GUI stack OK`，exit 0 |
| `odgui --help` | 经 PATH 解析正常 |
| **真实启动**（`scripts/odgui_launch_check.py`） | 窗口 1294×858、951 种颜色；`WM_CLOSE` 干净退出，**exit 0** |

该脚本用 `WM_CLOSE` 而不是 `terminate()` 关闭，因为只有前者会走 `closeEvent`——
而"对接进行中关窗导致 `QThread` abort"正是 §3.7 第 46 条要防的情况。

> 一度以为存在"结构没有居中"的取景 bug。**那是测量错误，不是渲染错误**：
> `grabFramebuffer()` 返回**设备像素**（本机 DPR 1.25，981×984），
> 而我拿控件的逻辑尺寸 785 去比，于是凭空得到 25% 的偏移。
> `scripts/viewport_framing_check.py` 现在按图像尺寸判定：
> 实测内容中心偏移 **−0.1%**，`frame_all` 前后一致。
> "内容触到边缘"是正常的——22 Å 搜索盒比分子大，本来就该铺满视野。

### 3.10 改名过程中发现并修复的 bug

本项目把命令名收敛成两个——`odgui` 与 `odcli`——并把包名定为 `opendocking`。
改名不是纯文本替换：**改名漏掉了一整类引用，而现成的验证脚本正好覆盖了它们**。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 50 | `examples/` 下 4 个脚本、`scripts/workbench_interaction_check.py` 全部 `NameError` | 改名脚本重写了 `import X` → `import opendocking`，但**没有**重写 `X.Receptor` 这类**用法**。import 成功、执行时才炸 | 逐个改为 `opendocking.`；`examples/*.py` 与 `scripts/*.py` 现在全仓库无残留用法 |
| 51 | `robustness_check.py` 的三个 "panic 不杀进程" 用例**一直在假通过** | `run_in_subprocess` 只看 `returncode not in (0, 1)`。改名后子进程因 `ModuleNotFoundError` 退出 1，于是被当成"引擎干净地抛了可捕获异常" | 增加守卫：子进程 stderr 出现 `ModuleNotFoundError` / `NameError` 直接判 FAIL，并说明"什么都没测到" |
| 58 | CI 的 `gpu` 配置 clippy 失败，而本机通过 | 本机 rustc 1.87 **没有** `mismatched_lifetime_syntaxes` 这条新 lint；CI 用 `@stable`（1.98）有。只有开 `--features gpu` 才编译到那段代码，所以 default 配置的 job 是绿的 | `binding_entry` 显式命名输入与输出生命周期；本机工具链升到 1.98.1 与 CI 对齐后重跑 |

第 51 条比第 50 条更值得记：**一个无法区分"引擎抛了干净异常"和"脚本自己坏了"的测试，
等于没有测试**。守卫本身也做了反向验证——故意让子进程 import 一个不存在的模块，
确认它被判 FAIL 而不是 PASS。

> 发现 50、51 的过程值得记下来：`opendocking.tests` 37 项全绿，
> 但它们测的是**包内**代码；`examples/` 与 `scripts/` 在包外，
> 不在任何测试的收集范围内。改名改的恰好是包外的编排层。
>
> 58 条则说明另一件事：**"本地绿"不等于"CI 绿"**。本地工具链比 CI 旧，
> 新增的 lint 根本不会触发。工具链版本应当与 CI 对齐，否则验证是有缺口的。

### 3.13 CPU/GPU 一致性单测的阈值本身就是错的

推上 GitHub 后 CI 第一次真正跑完，`engine / bindings (gpu)` 在 Python 测试这一步变红——
**不是 clippy，也不是引擎算错了**：

```
AssertionError: GPU and CPU disagree by 0.000114503
assert 0.00011450314968897146 < 0.0001
```

本机 RTX 3050 上同一个断言是绿的。量了实际数字才看清根因：

| 量 | 值 |
|---|---|
| 该批构象的得分量级 `max\|cpu\|` | **1042** |
| 本机（NVIDIA）最差绝对误差 | 3.81e-05 |
| CI（软件光栅化）最差绝对误差 | 1.15e-04 |
| `f32_eps × 量级` | **1.24e-04** |
| CI 相对误差 | **1.10e-07** ≈ 0.92 个 f32 ulp |

原来的断言写的是 `worst < 1e-4`，一个**固定绝对阈值**。而这些构象是随机摆的，
相当一部分伸出盒子，得分到几百，单精度下一个 ulp 就有 `1e-4` 量级——
**阈值比它要检查的算术本身还小**。所以它不是"CI 更严所以暴露了问题"，
而是这个阈值在任何机器上都不可能可靠：NVIDIA 的编译器碰巧落在下面就绿，
换一个就红。误差本身完全在单精度舍入范围内，引擎没有问题。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 58 | gpu job 的 `test_the_gpu_batch_path_agrees_and_reports_itself` 在 CI 挂、本机绿 | 断言用固定绝对阈值 `1e-4`，低于该批得分量级下一个 f32 ulp（1.24e-4）。机器换了、shader 编译器换了就必红 | 改为**相对**阈值：`worst <= 1e-5 * max(1, max\|cpu\|)`，并在注释里写明为什么绝对阈值在这里没有意义 |
| 59 | `examples/audit_poses.py` 的 `gpu_gap > 1e-3` 是同一个错 | 同一类：绝对阈值套在可能带 clash 的位姿上（clash 位姿能量可达几百） | 一并改为相对阈值，flag 里带上相对数值 |
| 60 | `docs/ARCHITECTURE.md` 声称 GPU 与 CPU 结果"逐位相同" | **不实**。拆分只保证**分子内项**逐位相同，分子间插值是单精度的，测得相对误差 ~1e-7 | 改正说法，并补上两个平台上的实测相对误差 |
| 61 | `core.evaluate_conformations` 的 docstring 写"agrees to about 1e-8" | 同上，且 1e-8 是在**得分很小**的位姿上量的绝对值，被当成了普遍结论 | 改为"相对误差约 1e-7，量级 10 的得分上约合 1 微卡/摩尔" |
| 62 | workbench job 在 "Install system libraries" 6 秒失败：`E: Unable to locate package libxkbcommon-x11` | 包名漏了 `-0` 后缀。core job 里写的是对的，gui job 是从别处复制时漏掉的 | 改为 `libxkbcommon-x11-0` |

这一条与 §3.10 的教训是同一类：**断言写死的数字，必须问它"这个数字和什么量纲比"**。
"GPU 和 CPU 相差小于 1e-4" 读起来像一个物理精度声明，实际上它是一个
**关于测试机器 shader 编译器的断言**。

#### 相对阈值的取舍，以及它的反向验证

把阈值改成相对的不是"放宽"，所以必须证明它**仍然能抓住真 bug**。
对 10 个点逐个核对了新阈值的判定：

| 情形 | 最差绝对误差 | 得分量级 | 判定 |
|---|---|---|---|
| 本机 NVIDIA（实测） | 3.81e-05 | 1042 | pass（余量 **91×**） |
| CI 软件光栅化（实测） | 1.15e-04 | 1042 | pass |
| 无 GPU，CPU 回退 | 0 | 1042 | pass |
| 注入 1e-3 相对误差的真 bug | 1.04 | 1042 | **FAIL** |
| 注入 1e-2 相对误差的真 bug | 10.4 | 1042 | **FAIL** |
| 注入 0.01 绝对误差 @ 得分 −10.4 | 0.01 | 10.4 | **FAIL** |
| 注入 0.01 绝对误差 @ 得分 −9.8 | 0.01 | 9.8 | **FAIL** |
| 得分 0.5、f32 噪声 | 6e-08 | 0.5 | pass（`1.0` 下限生效） |
| 得分 0.5、注入 0.01 | 0.01 | 0.5 | **FAIL** |

**纯相对阈值有一个代价，这里明说**：在得分 1042 上，`0.01` 的绝对误差是
`9.6e-6` 相对误差，会**通过**。之所以接受，是因为 `+1042 kcal/mol` 意味着
构象被摆到了网格之外很远，那是一个没有人会当作结论的数字。
而在**真正会被解读的得分区间**（对接位姿约 −10 kcal/mol），
同样的 `0.01` 绝对误差比阈值大 100 倍，照样被抓住——上表后两行就是这个。

没有再加一道绝对上限：任何在量级 1042 上不误伤的绝对上限都 ≥ 0.01，
而在得分 −10 上它会比相对判据更松，反而**削弱**测试在关键区间的牙齿。
单精度舍入本身就是相对量，加绝对上限会把刚修掉的那个 bug 请回来。

### 3.15 修好 3.14.1 之后，暴露出的更深一层问题

`from_pdbqt_str` 修好之后，`robustness_check.py` 里"两个原子重叠"这一项**从绿变红**。
不是它本来是错的，是**它此前是被那个 bug 满足的**：`from_pdbqt_str` 无论传什么都报

把 bug 修掉，才第一次真正测到解析器——于是测出一个新问题。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 66 | 两个原子落在同一坐标的配体被**静默接受**，能量、梯度、批量打分、完整对接全部返回有限值，甚至给出一个 −0.61 kcal/mol 的"最优构象" | 引擎没有原子间距校验。这类结构不会崩：重叠对要么是成键邻居（本来就被排除在分子内项外），要么被短程钳位挡住，所以每一个数字都是有限的 | `Ligand::from_molecule_with` 增加 `MIN_ATOM_SEPARATION = 0.5 Å` 下限并拒绝，错误信息给出两个原子的名字、序号和实际距离。新增两个 Rust 测试：重叠必被拒；真实几何不得被误拒 |

配一个测试把这个余量钉住：构造一个最短接触为正常 C–H 键长（1.09 Å）的分子，
断言它通过——**如果这个下限哪天被调高，测试会先红**。

这个 bug 比崩溃更危险。崩溃你看得见；它给出的是**有限、合理、但建立在不存在的

### 3.17 3D 显示方式：键的正确性，以及为此挖出的四个缺陷

新增 `display` 选择器：空间填充 / 球棍 / 键线式 / 条带 / 卡通。
真正的工作量不在画，而在**键必须连对原子**——这正是球棍模型最容易骗人的地方。

原来的规则只有一句："距离小于 1.95 Å 就连"。对二十个原子的药成立，
对蛋白则是灾难：crambin 上这条规则会造出 **48 条跨残基键**。

| 配体 / 姿势（有 `ROOT`/`BRANCH`） | 文件**声明**的树 | 16 键，全部物理可能 |
| 蛋白质 | **残基模板** + 肽键 | 389 键，**跨残基键 0 条**（距离法是 48 条） |

#### 姿势文件自己声明了一根不存在的键

姿势的 PDBQT 里有一个分支：

```
BRANCH  11  13
    ATOM 13 C13 / ATOM 14 O14 / ATOM 15 O15 / ATOM 16 H16
```

PDBQT 规定块内原子**依次成链**。但羧基的化学是 C13(=O14)(−O15−H16)——一个**分叉**，
AutoDock 用**嵌套 BRANCH** 表达，而本项目的写入器把它写成了平链。
于是文件声明 O14–O15 成键，而它们相距 **2.23 Å**。

修 bug 前，这个文件给出 **22 键**，C7 有 6 根键（碳最多 4）。修之后 **16 键**，
全部物理可能，无过价原子。处理原则是**声明决定拓扑，几何可否决**：
一根 2.2 Å 的氧–氧键不管谁声明的都不画，并且报告出来。

**写入器本身还没修**（需要嵌套 BRANCH），已写进 CHANGELOG 的 Known limitations。

原因是逐残基用 CA→CB 定向，而相邻残基之间这个向量摆动几十度，
截面在每一步都转一次。改成**平行传输**（沿样条传递朝向）后正常。
这一条是看截图才发现的，任何断言都发现不了——"每个顶点都靠近 CA"
和"画面是一根连续的带"是两回事。

### 3.18 推送后的 CI 抓到的缺陷：一个从未通过的检查

上面这一版推上去之后，CI 的 `Real launch, then close` 是红的。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 74 | `Real launch, then close` 在 CI 上必然超时失败（60 秒后 `exit code: -15`、`closed via: none`） | CI 用 `xvfb-run`，**只开显示、不起窗口管理器**。而 `wmctrl` 是向窗口管理器要 EWMH 的 `_NET_CLIENT_LIST`——没有 WM，它连窗口都列不出来，循环只能空转到超时 | **找**窗口改用 `xdotool search`：它走 `XQueryTree` 直接遍历 X 树，不需要 WM |

### 3.19 一项检查会静默消失，而不是被记为跳过

给步骤改名成「75 checks」之后，CI 报的是 `74 checks`。

差的这一项不是某台机器上少跑了什么，而是**这条检查在条件不满足时压根没有被登记**：

```python
if len(drawn) == 3:
    check("the protein ribbon is a different picture from its atoms", ...)
```

无头 runner 的 framebuffer 读回空白，`drawn` 是空的，于是 `if` 不成立，
这一项既不是 PASS 也不是 SKIP，而是**不存在**。
总数从 75 变成 74，而 74 这个数字没有任何人会去质疑——
它看起来就像「这个版本少了一项功能」。

同一份脚本里还有第二处（`if hydrogens and carbons:`），本地姿势文件里两者都有，
所以本地永远走不到 `else`，一直没暴露。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 78 | CI 报 74 项而本地 75 项；差异无处可查 | 两处检查用 `if` 守卫，前置条件不满足时**不登记结果**。少一项和「这项没跑」在输出里长得一样 | 两处都补 `else: skip(..., 原因)`，总数在任何环境下都恒为 75 |

这和 §3.18 的第 76 条是同一类：**恒真或可消失的断言不提供任何信息**。
区别只在于一个恒真、一个恒缺，而后者更难发现，因为它看起来像范围变小了。

**反向验证**：把 `PIXELS_OK` 强制为 `False`（复现 runner 条件）跑一遍——
改之前 `74 checks`，改之后 `61 passed, 0 failed, 14 skipped, 75 checks`，
通过数与 CI 实测的 61 完全一致，多出的那一项明确显示为 SKIP 并写明原因。
真实显示环境下仍是 `75 passed, 0 failed, 0 skipped`。

### 3.20 接触分析：让查看器从「看形状」变成「读结果」

在此之前，姿势放进受体的画面里，**埋在疏水沟里的姿势和粘在蛋白表面的姿势长得一模一样**。
区分它们的是打分函数，而画面上没有任何东西表达这件事。

新增 `opendocking.workbench.contacts`（纯几何，无 Qt、无显示）：

- **氢键**：H···受体 <= 2.6 A 且 D–H···A 夹角 >= 120°，**两个方向都查**——
  对接姿势里供体通常是**受体**（骨架 NH、丝氨酸 OH 伸向配体羰基），
  只看配体侧会漏掉大部分。
- **近接触**：重原子对 <= 4.0 A，排除氢（否则每个 C–H 都会报告一条）。
- 每个接触都带回距离和角度，**阈值可以收紧而不必相信它**。
- 父原子定不下来的氢**一律不画氢键**——没有角度可算的键就是没验证过的键。

实测：布洛芬对接到 crambin（9 个姿势，最优 **-5.5 kcal/mol**），
**THR 2 的羟基氢 donate 给配体羧酸根**（2.55 A / 137.6°）被识别为氢键并排在残基表首位，
共 48 个接触、7 个残基。

**必须说清楚的两件事：**

1. **1L96 是个负面结果。** T4 溶菌酶 L99A 是**为了造出一个埋藏空腔**而改造的
   （把一个笨重残基换成丙氨酸），在默认 1.4 A 探针下本工具报告 **0 个密闭空腔**。
   原因清楚：那个空腔约 100 A³，而 1.4 A 的探针把每个原子都膨胀这么多，
   膨胀后的表面直接把它填满了。

   这不是「搜索不会找小空腔」，而是「默认探针太钝」——而钝的默认值是对的：
   0.5 A 探针会把表面沟槽闭成几十个假空腔，比没有答案更糟。

   所以新增 `pockets.cavity_sensitivity()`，并且**在没有找到密闭空腔时如实说出来**：

   ```
   No sealed cavity at the default 1.4 A probe. Against a smaller probe:
   1.4 A -> 0, 1.1 A -> 0, 0.9 A -> 1, 0.7 A -> 1, 0.5 A -> 1
   ```

   **一个空结果必须能被行动**，否则它只是一句废话。

2. **耗时随尺度增长很快。** 4779 原子要 11 秒。网格边长随蛋白尺度增长、
   洪水填充迭代到不动点，成本大致按体积走。这就是第 93 条必须用线程的原因。

用自动 box 对接得到的姿势与参考姿势 **RMSD 4.24 A**。
**能量复现了，姿势没有复现。** crambin + 布洛芬存在接近简并的结合模式，
落进另一个极小点是能量面的性质，**不是 box 放错了地方**——box 确实装下了
全部 16 个配体原子，而且由给参考姿势供氢键的那个残基衬里。

所以检查里断言的是**能量**，RMSD 只被**记录**、不加任何断言。
断言一个小的 RMSD 等于断言这一次运行恰好落在这个极小点上，那是运气；
**靠运气通过的检查比没有检查更糟**。

**这个数字动过。** 原来是 −5.42 / 3.93 A，现在是 −5.36 / 4.24 A——
不是因为引擎变了（Rust 一行没动），而是因为**对接用的 box 变了**：
修好口袋排序之后，这条检查不再用「离配体质心最近的那个位点」，
改用「**box 装得下全部原子**的那个位点」，而这两个在 crambin 上不是同一个。
顺手更新，不写成「一直如此」——报告里出现一个和自己上次不一样的数字时，
不解释它比数字本身更糟。

#### 必须看图

`scripts/contacts_screenshot.py` 输出两张图（全景 + 聚焦到 THR 2）。
**疏水接触的配色问题就是看出来的**——断言全过时，48 条里有 16 条是隐形的。

`scripts/pockets_screenshot.py` 输出两张图。
**相机构图问题就是看出来的**：第一版按位点尺寸（7 A）取景，相机落到 18 A，
正好在蛋白自身的表面原子**里面**，画面是几个碳的特写、box 边界全在屏外——
数字全对，看不出 box 到底在不在合理位置。改成按 box **对角线**取景才看得见。

#### 3.7 无回对接基准挖出的四个缺陷

这一轮的起因是一个**负面结果**：把一个已经结合在晶体结构里的配体重新对接回去，
用口袋搜索自动选出的 box，**四个真实复合物上全部失败**，RMSD 18–29 A。
而用结合配体自己推出的 box，两个成功（1.17 A、1.19 A）。

一个功能「在四个真实复合物上 0/4」而它自己声称的用例全过，第一反应应该是
**测量本身错了**，而不是功能坏了。先查测量。

**结果：两者都错了。** 测量有两个缺陷，功能有两个缺陷。四个都记在这里。

#### 缺陷 98：口袋搜索与对接引擎看的是两个不同的分子

`scripts/redock_benchmark.py` 原来在**原始 PDB**（全部链）上搜口袋，
在 `prepare_receptor` 的输出上对接。而 `prepare_receptor` **只保留最大的片段**，
其余静默丢弃——它会发一条 warning，但基准脚本把 warning 静音了。

1HVR（HIV 蛋白酶同源二聚体）实测：

| 输入 | 原子数 |
|---|---|
| 原始 PDB（两条链） | 1826 |
| `prepare_receptor` 输出 | **621** |

也就是说，那一行「29.27 A 的失败」里，有多少是搜索的错、有多少是**测了一个
不存在的分子**，根本分不开。**一个把两件事混在一起的测量，两个数都不能用。**

修法：受体先收窄到配体所在的那条链，制备一次，然后**口袋搜索和引擎读同一个文件**
——这正是工作台自己的行为（它在即将对接的那个受体上搜索，而不是在用户碰巧打开的
那个文件上）。脚本现在每一步都打印剩下的原子数，制备掉了片段时**打印一条 WARNING**，
而不是让读者以为那 1826 个原子还在。

#### 缺陷 99：标签前的各向同性膨胀把每一个真位点都并进了蛋白外表面

这是 0/4 的真正原因，也是最难找的一个。

`find_pockets` 在做连通域标记**之前**，把埋藏掩码各向同性膨胀一个体素。
本意是让单层「薄片」变成有体积的团块。实际效果是**反向的**：表面沟槽本来就是
一个体素厚，膨胀一个体素就**跨过沟口并进了外表面**。然后这一坨东西因为体积超限
被切掉，**把里面的真位点一起带走了**。

实测，四个复合物上「配体自己所在的那个连通域」，膨胀前 / 膨胀后：

| 复合物 | 膨胀前 | 膨胀后 |
|---|---|---|
| 1STP 生物素 | 314 体素，box 1305 A³ → **保留** | 4905 体素，box **71909 A³** |
| 3PTB 苯甲脒 | 698 体素，box 10161 A³ → **保留** | 4114 体素，box **77893 A³** |
| 1HVR XK2 | 1063 体素，box 8008 A³ → **保留** | 6303 体素，box **109965 A³** |

膨胀前都是正常口袋大小，膨胀后都是「整个蛋白的一坨」。**膨胀从「把薄片变成团块」
变成了「把口袋并掉」**，而且是静默的：列表看起来完全正常，只是里面没有真东西。

修法：去掉标记前的膨胀。改完之后，**四个复合物里结合配体的位点全部排到第 1**，
而改之前它们**一个都不在列表里**（不是排错名次，是根本没有）。

#### 缺陷 100：体积上限量的是包围盒，扔掉的是真的口袋

`max_volume` 原来作用在位点的**包围盒体积**上。这在两个方向上都是错的：

* **蜿蜒的裂隙**包围盒巨大、内部空间很少。1HVR 的真位点是 **8008 A³ 的盒子、
  544 A³ 的口袋**——上限一刀把它切掉。合成的「折角槽」夹具复现同一形状：
  **9698 A³ 的盒子、1016 A³ 的空间**，旧上限必丢。
* **平坦的表面片层**包围盒不大、体素很多，恰好是相反的失真方向。

改用量**真实体素体积**（`voxels * spacing³`），并给 `Pocket` 加了 `volume` 字段
让这个量能被读出来。GUI 口袋表因此加了第五列 `vol Å³`——排序用的是
`volume^(1/3) × burial`，这两个量原来**一个都看不见**，所以列表看上去像是随便排的。

顺带一个诚实的副作用：crambin 上那个上限**现在什么都不删**（16 → 16，旧的膨胀下是
23 → 20）。因为它本来就是在替膨胀擦屁股。检查里现在**显式断言这件事**——
一个悄悄不再触发的过滤器就是这么烂掉的。

#### 缺陷 101：一个断言是运气，被换成了断言事实

`pockets_check.py` 里原来有一条：crambin 的布洛芬位点「排在第 2」，
且「由独立接触分析判定为供氢键的 **THR 2** 衬里」。

拆开看，这条断言是**巧合**。那个位点只有 **12 A³**；crambin 上有三个更大的表面
团块（88、56、20 A³）排在它前面。旧代码里它之所以是第 2，**纯粹因为那条包围盒
体积上限顺手切掉了那三坨**。上限不是排名能力，换掉膨胀之后它就不管用了——
**同一个位点变成第 9**。THR 2 确实还在它的衬里里，但那是因为位点还是同一个位点，
不是因为它排在第 2。

现在断言的是**事实**而不是巧合：

* 有某个位点的 box 装下**全部 16 个**原子（量出来的，第 9 名，12 A³）
* 它**不是**第一个——并把原因写进检查的说明里
* 它的衬里与**独立算出来的**接触列表**重合 6/7**（独立算 = 任何原子在该姿势
  4.5 A 内的残基；位点的衬里 = 从口袋算的。两次不相干的计算对上，比任一次单独
  可信都强）

同时把「每个画出来的点都在 4.5 A 内的衬里残基旁边」这条**改掉了**。它以前能过是
**因为膨胀把每个点都往原子方向拉了一格**。膨胀去掉后最远的一个点离原子 4.91 A——
这是**对的**：一个点之所以属于某个位点，是因为沿某个轴两侧 3.0 A/spacing 体素内
有蛋白，掩码的保证本来就比 `LINING_MAX = 4.5` 宽。`LINING_MAX` 是**报告阈值**，
拿它当几何保证去断言，是在断言掩码从没承诺过的东西。

换成断言两条真正成立的：每个画出来的点都在**自由空间**里（到最近原子膨胀面的
净空 > 0，逐原子算，不是拿单一半径），以及**报告的衬里恰好等于** 4.5 A 内的
残基集合——从坐标重算，不读回来，这样 `_lining` 里的 bug 无法自己和自己对上。

#### 无回对接基准：修完之后诚实的数字

`scripts/redock_benchmark.py`。**不是 CI 门禁**（要联网，而且没有可诚实判定的真值）。
受体收窄到配体所在链、制备一次、搜索与引擎读同一个文件之后：

| 复合物 | 配体原子 | 结合配体盒 best | 口袋 top-1 盒 best | 位点排名 |
|---|---|---|---|---|
| 1STP / 生物素 | 16 | **1.17 A** | 21.56 A | 2 |
| 3PTB / 苯甲脒 | 9 | **1.19 A** | **1.26 A** | **1** |
| 2NNQ / T4B | 36 | 3.50 A | 3.63 A | **1** |
| 1HVR / XK2 | 46 | 2.88 A | 21.24 A | **1** |

`best < 2 A`：结合配体盒 **2/4**，口袋 top-1 盒 **1/4**（修之前是 **0/4**）。
**位点排名 1、1、1、2** ——搜索在四个复合物上都**找对了地方**。

第三列（口袋选中**那个真的装着结合姿势**的位点的 box）在 1STP 上是 7.77 A，
对比 top-1 的 21.56 A：**1STP 是排序问题，不是搜索问题**。

#### 还有一个：box 需要的采样量随体积变化，之前是写死的

3PTB 的位点 box 是 **39 × 26 × 41 A**（41,600 A³）。固定 exhaustiveness 16 时
读出 **12.88 A**，同一个 box 在 64 时读出 **1.26 A**，128 时还是 1.26 A——
**两秒**。也就是说第一版把一个**采样不足**的问题读成了**box 太大**。

exhaustiveness 是蒙特卡洛步数，41,000 A³ 的 box 里同样的步数摊得比 8,000 A³ 稀，
所以写死的值会**悄悄地对每一个大 box 采样不足**。现在按体积的 2/3 次方从
`{16, 32, 64, 128}` 这几级台阶里选，并且**把实际用的值打印出来**——1.2 A
是在 40,000 A³ 的 box、exhaustiveness 64 下找到的，和在 3,000 A³、16 下找到的
不是同一个断言，表格里只印「1.2 A」会藏掉这个区别。

1HVR 即便如此仍然最差（21.24 A，46 原子的柔性配体 + 30×38×32 A 的 box）。
**这个如实留着，没有调参把它弄好看。**

#### 缺陷 102：一个像素检查绕过了守卫，在无头机上误报失败

CI 抓到的，`workbench (best effort)` 这一步真的红过。比对上一次运行才发现
**它上一轮就已经在失败**——不是这轮引入的，但也没人去管。

`workbench_interaction_check.py` 里所有像素类检查都走 `pixel_check()`，
它在帧缓冲读回空白时 **SKIP**——CI 的无头机正是这种情况，所以 15 项跳过。
只有 `site volume` 那一项直接调了 `check()`，于是**同样一台渲染不出画面的机器
上，15 项跳过、1 项报失败**：一台根本画不出东西的机器被要求证明开关改变了画面。

改成走 `pixel_check()`。**守卫是双向的**——有真实 GPU 的机器上，勾选框不改变画面
仍然 FAIL，只有环境无法作答时才 SKIP。

顺带修掉这轮自己引入的那条：`the table has the four columns` 现在是五列
（多了排序用的 `vol Å³`），断言跟着更新，并加了「每行都真的有数字、且都不超过
体积上限」——一条空列和没有这一列是一样的。中间还写错过一次断言
（`"88 Å³"[:-1].isdigit()` 得到的是 `"88 Å"` 而不是 `"88"`），**是测试错了不是代码错了**，
改成按空格切开单位。

#### 缺陷 103：一个用户报告的颜色，图例里没有

报告原文：**「导入受体之后，发现有个 box 盒子，里面有几个紫色圆球」**。

复现：只加载一个受体，别的什么都不动。172 个球体，`COLOR_POCKET = (0.85, 0.35, 0.75)`，
`show_pocket = True`，盒子在第 1 个位点上——**全部是预期行为**。加载路径会
`find_pockets_now()` 然后 `selectRow(0)`，选中行就把盒子放上去、把点云画出来，
所以它在用户还没动手之前就出现了。

**这不是渲染 bug，是图例缺陷。** 图例只有四个**虚线**交互色的条目，
点云这种**实心体**的颜色一条都没有。于是画面里出现了一种**屏幕上没有任何文字说明的颜色**，
第一次读到的就是「那是什么球」。

「旁边有个 `site volume` 勾选框」和「这个颜色就是 site volume」不是同一个断言，
**两者的差别正是图例存在的理由**。修法：图例加一条 `● site volume`，
用**圆点**而不是短横线，因为它是体不是线——色标的形状本身就是图例在声明的内容。
色标颜色从渲染器用的同一张表读，不是抄一份。

新增四条检查，让这种事不能再发生：图例**点名** site volume、它的色标颜色
**等于**渲染器实际用的 `COLOR_POCKET`、四种交互色都在图例里、**每个色标都有名字**
（不允许出现没有文字的裸颜色）。

#### 把「采样量必须随体积走」这条教训搬进产品

§3.7 里那条结论只落在了**基准脚本**里，产品本身没享受到：工作台会把自动放置的
大盒子配上一个为小盒子调的**固定 8**，而口袋搜索**本来就会**给出一条 39×26×41 Å
的裂隙盒子。用户在一个 40 Å 的盒子里用 8 跑搜索，拿到一个坏姿势，
而**坏姿势和盒子放错了在界面上长得一模一样**。

规则搬进 `opendocking.core.exhaustiveness_for_box`，
因为工作台、`odcli` 和基准脚本需要的是**同一条**规则——
一条规则三份抄本就是它们开始互相矛盾的方式。合并时发现基准脚本那份
**已经漂移**了：它的台阶从 16 起，引擎的从 8 起。

- **工作台**：输入框跟随盒子变化，**但用户一旦自己动过就永久停手**。
  一个会把你填的数字改回去的控件比一个从不帮忙的控件更糟——
  你会开始不信那个唯一在跑完之前看不到效果的数字。唯一调用点是
  `_on_box_changed`，也就是盒子唯一的改变入口，所以只有一条路径能提建议。
  设置时用 `_updating_exhaust` 守卫：程序自己 `setValue` 也会发
  `valueChanged`，没有守卫的话**建议会在第一次生效时把自己标记成用户编辑**，
  从此再也不生效——而那看起来正好像这个功能从没写过。
- **`odcli`**：不给 `-e` 时按盒子算，并**把用的值和为什么印出来**。
  它以前在帮助文本里是个常数，而一个会随盒子变的数字必须被说出来，
  否则用户会以为固定是 8，然后困惑于为什么两次「同样的」搜索不一致。
- **基准脚本**：删掉自己那份，改用引擎的。

指数取 **1（线性）而不是拟合幂**。手上只有一个标定点，它说 5.2 倍大的盒子
至少需要 8 倍的步数；幂律可以被拟合得刚好对上，
而**用单个测量拟合出来的幂律是一种假装自己知道**。线性是个整数，
略微偏保守，而且是脑子能装下的「每 8000 Å³ 8 步」。

反向验证：每一级台阶都必须**可达**，否则这个规则就是一个穿着公式外衣的常数。
用一组立方体边长扫描，而且**不能**只取几个整数——
20、30、45 这几个会干净地跳过 16 和 64，
于是一条偷偷跳过台阶的规则也能「看起来没问题」。

#### 一个没能复现的偶发失败，如实记下来

加完图例检查后的第一次运行里，`the interaction toggle is on by default`
**失败了一次，而且 detail 是空的**。

- 它**没有 detail 参数**，所以失败时什么线索都没有——**一条偶发失败又无法诊断的检查，
  等于一条你会慢慢学会忽略的检查，而被忽略的检查可以永远错下去**。这是检查本身的缺陷。
- 补上 detail：勾选框状态、`viewport.show_contacts`、接触数、口袋搜索线程是否还在跑。
  补完之后连跑三次全部通过，三次的 detail **完全一致**
  （`checkbox True, show_contacts True, 48 contacts, pocket thread running False`）。
- 5 次里失败 1 次，**我没能复现，也就没有根因**。不写成「已修复」。
  目前只能说：偶发，触发条件未知，检查现在会报出它所断言的状态。

### 3.22 让子 agent 去打破上一轮的成果，而不是去延续它

前三节里挖出来的东西都是**功能对不对**。这一节挖出来的是另一类：
**检查本身在骗人**，而这类缺陷只有在有人**专门去破坏**的时候才会现形。

我派了一个 agent 去做变异测试（把已知正确的代码改坏，看检查会不会响），
外加另外三个 agent 去做新功能。前者的结果比后三个加起来更值得记。

#### 检查守着一个根本没接线的控件

`exhaustiveness_for_box` 规则本身测得很好——四个变异全部被抓。**但工作台里
调用它的那段接线，一行都没有被测过**：`_suggest_exhaustiveness`、
`_exhaust_is_default`、`_updating_exhaust` 这三个名字在**整个仓库的检查脚本里
一次都没出现过**。于是删掉守卫、让函数立刻 return、闩锁失效、写死 `want = 8`
——**四个变异全部停在 135/135**。

一个可以正确工作、也可以完全死掉而在检查里长得一模一样的东西，
和没有测试的东西是同一个东西。补完之后四个变异分别转红 9 / 9 / 4 / 6 条。

#### 三种坏掉的检查

| 形态 | 表现 | 为什么它比没有更糟 |
|---|---|---|
| **恒真** | 两条 check 的布尔表达式**逐字相同** | 它把总数撑大，于是总数看起来是健康的 |
| **惩罚正确代码** | 一条断言「这个位点不是第一」 | **四个变异把排序改好之后它变红**。这个仓库一直在对抗「把结论冻结进断言」，而这条是同一个错误的自动化版本 |
| **藏在守卫后面** | 收紧体积上限，套件从 118 掉到 84 | **34 条检查根本没执行，运行照样报告全部通过**。现在 `EXPECTED_CHECKS` 把总数钉死，并且这条钉子本身是自描述的 |

#### 一个 agent 拒绝了它被要求做的事

我要求给「薄片口袋」加守卫，否则 §3.7 里那个「下面的章节会给出答案」的承诺就是空的。

它先把缺陷复现了（一条 1.2 A 宽的夹缝被报成 rank 1、1127 A³ 的口袋），
然后量了**薄片和 crambin 唯一的实测结合位点**——同为 4 层、间距同为 0.8 A。
腐蚀之后：薄片剩 128 体素，**真位点剩 1**。

于是**它没有加这个守卫**，改为把局限钉进 `Pocket.thickness` 并在文档里写明
这个量区分不了两者。**任何一个能删掉薄片的守卫都会删掉唯一的实测结合位点**——
按我原话说出来的「修好」会把唯一有效的数据毁掉。

#### 一个 agent 推翻了我的「修正」

我告诉它 `Chem.PathToSubmol` 会**下溢**（要 11 个原子只给 9 个），并说下溢比多原子更糟。
它查了，**说我是错的**。我复测：

```
CCO + AddHs atom count: 9          <-- 我探针注释里写的 "11" 是我假设的，从没测过
  req=11 (invalid)  -> got=9        <-- 无效请求，不是下溢
Zn+2 1 原子: req=[0] -> got=0       <-- 真正的下溢，是它找到的
```

那个「11」是我写进注释的假设，我从未测量。**它是对的，我的那条「修正」已撤回**，
而真正重要的方向——单原子分量返回空分子，于是只含水或离子的受体会准备出
**什么都没有**的结果——由它先发现。

同一次会话里我还给两个 agent 发过**错的缺陷编号**（110、107，实际是 103），
第三次干脆改成让 agent 写 `<!-- DEFECT -->` 占位、由我统一编号。
**编号从四个人手里各起一次 104，必然撞号**，而两份编号不同的文档比一份错的还难读。

#### 「从未执行过的语句」：40 → 17

其中一个 agent 用 `trace` + `ast` 扫了整个 `prep.py`：**402 条可执行语句、
362 条跑过、40 条从未跑过**，逐条分类。最大的整块空白是
**`prepare_ligand` 完全没有检查脚本**——而那是用户第一次运行会走的路。

补完一轮之后：**40 → 17**。剩下的 17 条里有 7 条是**设计上就不该跑**的守卫
（各自已写明要什么条件才会发生）、4 条是需要 RDKit 抛错的兜底分支
（**没有伪造 RDKit 失败来覆盖它们**，而是列出来），剩下的是电荷兜底与一行
`summary()`。

它同时发现自己上一轮说的「`_load_unsanitised` 能走到重试」也是错的——
那个夹具根本 sanitize 直接就过，于是**那条检查并没有证明重试跑过**。
换成真正的 kekulisation 失败夹具（六元环、一个碳上三个双键），
并把三件事**分别**断言。只断言结果的话，一次本来就成功的首读就能满足它。

#### 量到了但没有「修」的东西

**电荷表不中性**：合并非极性氢时没有把该氢的部分电荷并进母原子，
苯因此合计 -0.3736 e、ibuprofen -0.6036 e。**没有改**——
改了会动到引擎至今产出的每一个分数，那是人的决定而不是测试的副作用。
现在每次运行都把这个数打出来，并且**既不断言它是缺陷，也不断言它是对的**。

还有「1HVR 仍是最差案例」（ex 64 → 21.24 A，ex 128 → 10.53 A）、
「二级结构的 39/46 对照的是硬编码标注而不是实跑 DSSP」、
「地图内存是引擎的估计式而不是实测 RSS」——**都如实留着。**

#### 这一节真正学到的东西

前三节里，每个缺陷都是**做错了什么**。这一节里大部分缺陷是
**做对了、而且检查还说它对**。

- 规则写对了，接线没测——**功能是对的，测试是空的**
- 上限写对了，守卫藏在 `if` 后面——**过滤器是对的，34 条检查是假的**
- 守卫该加，加了会毁数据——**建议是对的，执行会是错的**
- 探针写对了，注释里的数字是假设的——**测量是对的，结论是编的**

最后一条是我自己犯的。**没有任何一个单元测试能抓到「我以为我测了」**。

## 5. 结论

**可以据以使用的部分**：Rust 引擎的数值正确性（106/116 测试、两配置零警告）、
CPU/GPU 数值一致性（相对误差 ~1e-7，约一个 f32 ulp；两个不同平台实测，
见 §3.13）、Python 绑定与零拷贝契约、
CLI 全部子命令、workbench 的真实渲染**与全部交互控件**、
畸形输入的安全处理、确定性与并行正确性、真实蛋白的完整预处理链路、
并写的输出能被自己的读取器完整读回。

**尚不能据以做出科学结论的部分**：任何"这个配体会结合到这个位点"的断言——
那需要 §2.1（与 Vina 交叉验证）和 §2.2（回对接），两者都还没做。
本轮修掉的打分函数缺陷（§3.2.1）让能量落在物理上正确的距离，
但**没有**让本工具变成经过验证的亲和力预测器。
